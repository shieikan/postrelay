# PostRelay

接続したツールから届いたXの公開投稿通知を、設定したDiscordチャンネルへ届けるセルフホスト用アプリです。アカウントごとの通知設定、キーワードでの絞り込み、送信履歴、永続キュー、再送、管理画面を備えています。名前は仮称です。X・Discord・TweetShiftとは無関係の独立したプロジェクトです。

**全コードはMITライセンス。セルフホストは無料です。** ホスティング版はStarter **$1.49/月**、Pro **$4.99/月**を予定しています。現在はローカル実装の段階で、ホスティング提供・契約・決済・SLAは未開始です。価格は採算確認後に確定します。

## すぐに試す

Python 3.9以降が必要です。外部PythonパッケージやNode.jsのインストールは不要です。

```sh
git clone https://github.com/shieikan/postrelay.git
cd postrelay
python3 -m postrelay --mode demo
```

[http://127.0.0.1:8765](http://127.0.0.1:8765) を開き、「デモを試す」を選んでください。架空の投稿通知で、通知設定の追加・編集・キーワード設定・通知の停止と再開・デモの利用プラン切り替えを試せます。デモはXやDiscordへアクセスせず、実際のDiscord送信先URLも保存しません。

## 自分の環境で使う

```sh
python3 -m postrelay --mode selfhost --data-dir ./data
```

管理画面でPostRelayのアカウントを作成します。メール送信・メール確認・パスワード再設定は未実装です。パスワードは12文字以上にしてください。登録キーを設定すると、キーを知っている人だけが登録できます。

```sh
export POSTRELAY_SIGNUP_KEY="$(python3 -c 'import secrets; print(secrets.token_urlsafe(32))')"
python3 -m postrelay --mode selfhost
```

初期状態は動作確認モードで、Discordには送信しません。実際にDiscordへ送信する場合だけ、次の起動方法を使用してください。

```sh
python3 -m postrelay --mode selfhost --live
```

実際の送信を有効にすると、通知設定に保存したDiscordの送信先URL（Webhook）へ送ります。送信先URLが未設定の場合は送信失敗として記録します。動作確認の記録は「送信なし」で区別します。メンションは既定で無効で、通知設定に指定したロールだけにメンションします。

このHTTPサーバーはローカル・小規模なセルフホスト向けです。公開ホスティングには、HTTPS終端、登録制御、バックアップ、アカウント復旧、監視、負荷検証、課金処理などの追加実装と検証が必要です。公開URLの指定だけで運営可能になるわけではありません。

## 通知元を接続する

「設定」の「投稿通知の受け取り方」を開き、PostRelayの受け取りURLを作成します。投稿通知を送るツールのWebhook送信先に、そのURLを設定してください。URLは認証情報を含みます。ログ・Git・公開設定には含めないでください。作り直すと以前のURLは使えなくなります。

受信する正規化JSONは、次の形式です。この例のアカウントと投稿は架空です。

```json
{
  "id": "12345",
  "author": "demo_studio",
  "text": "新機能を公開しました。",
  "url": "https://x.com/demo_studio/status/12345",
  "kind": "post",
  "visibility": "public"
}
```

`id`、`author`、`text`、`url`は文字列で必須。公開投稿のURLと投稿ID・Xのユーザー名の一致を検証します。本文は通知に含まれた範囲で、1〜4000文字です。`kind`は`post`、`reply`、`repost`。省略時は`post`として扱います。非公開通知・DMは対象外です。ただし、公開範囲の自己申告だけで公開性が証明されるわけではありません。公開アカウントだけを通知元に設定してください。

別のJSON構造は、「設定」の「連携ツールの詳細設定」で明示的に設定できます。たとえば、`text`に`notification.body`を指定すると、該当する項目から本文を読み取ります。設定に一致しない通知はHTTP 400となり、推測で送信しません。

### Angelic-Angelとの組み合わせ

[Angelic-Angel](https://github.com/sh1ma/Angelic-Angel)は、XのWeb Push通知を受けてWebhookへ転送する独立したMIT OSSです。PostRelayはそのコードを取り込んでおらず、汎用Webhook受信先として接続できる構成です。

Angelic-Angelの`WEBHOOK_ENDPOINT`にPostRelayの受け取りURLを設定します。2026年10月5日にXへの通知登録、Mozilla AutoPushへの接続、実通知1件の受信を確認しました。対象のTiboからの自然通知による自動配信はまだ確認していません。CookieはAngelic-Angelの非公開設定に保存し、PostRelayの管理画面や公開設定へ渡さないでください。接続時に使用した固定版と秘密情報のログ出力などを抑える修正は[integrations/README.md](integrations/README.md)を参照してください。

初回の通知形式を調べる場合は、ローカルのセルフホスト環境だけで `--capture-push` を追加できます。受け取りURLの `/api/hooks/` を `/api/push/` に替えてAngelic-Angelへ設定すると、受信JSONを非公開DBの `push_inbox` に保存し、Discordへ転送せずHTTP 202を返します。既存の認証トークンとURL作り直しによる失効が適用されます。ユーザーごとに最新20件まで、24時間を過ぎた記録は稼働中のワーカーが約1分ごとに削除します。停止中は削除も停止するため、再起動後の削除までDBに残ります。

同じローカル環境で `--relay-web-push` も追加すると、`data.url` または実通知で確認した `data.uri` の公開投稿リンクを受け取り、[Xの公開oEmbed](https://docs.x.com/x-for-websites/oembed-api)で投稿ID・投稿者・本文を確認してから転送します。通知に含まれる本文・名前は送信に使いません。DM・他アカウント・一致しないURLは送信対象外です。`--capture-push` を併用すると、確認できなかった通知だけを前述の制限で保存します。公開確認の一時的な失敗を保存後に自動で再確認する機能はありません。

oEmbedでは返信・リポストの種類を確認できないため、この受信方法は「返信を含める」「リポストを含める」が両方オンの通知設定だけに配信します。どちらかをオフにした設定には種類不明の投稿を送りません。他人が投稿したリポストをTibo本人の投稿として転送することもありません。通知される全投稿を網羅する保証や、画像・動画の展開はありません。

この受信方法を使う起動例です。受け取りURLの作成とAngelic-Angelへの設定が別途必要です。

```sh
python3 -m postrelay --mode selfhost --live --relay-web-push --capture-push
```

これらの受信方法は既定で無効です。通知に他のアカウントや非公開情報が含まれる可能性があるため、受信内容の保存に同意した本人の環境だけで使ってください。通知元の復号・認証情報を管理画面や公開ログに出さないでください。

Angelic-Angel自身はログインCookieを使ってXのWeb用エンドポイントへ登録します。MITライセンスはコード利用の許可であり、Xへの接続や商用運用の許可ではありません。[X利用規約](https://x.com/en/tos)などを確認する必要があります。通知の欠落率、遅延、全文・画像の含有範囲、規模の上限も未検証です。

## 送信と再送

- 同じPostRelayアカウント内の同じ投稿IDは、一度だけキューへ登録します。
- 通知と送信待ちデータの保存が完了してから、通知を送ったツールへHTTP 202を返します。
- HTTP 429は`retry_after`を待ち、通信失敗と5xxは指数バックオフで再送します。
- 最大8回で失敗となります。管理画面から手動で再試行できます。
- 未完了の送信はSQLiteに保存され、再起動後も継続します。期限切れの送信処理のリースは再取得します。
- ワーカーがDiscordへの送信成功直後・保存前に終了すると、再送で重複する可能性があります。Discordへ常に1回だけ送る保証はありません。
- 通知元が再送しない受信前の失敗は回収できません。Angelic-Angelの固定版には非2xx応答を成功扱いする箇所があります。同梱の修正パッチはその扱いを直しますが、通知元の永続再送キューやMozillaによる再配信は保証しません。

アカウントごとの永続データ分離は実装しています。同じプロセス・DBを共有するため、資源の隔離・大規模ホスティングの耐性を保証するものではありません。通知ログの自動保持期間・削除機能は未実装で、現段階では通知と履歴が継続保存されます。DBを運用する前に容量・保持・削除方針を決めてください。

## データと秘密情報

パスワードはPBKDF2-SHA256で保存し、セッション・受け取りURLのトークンはSHA-256のダイジェストだけを保存します。Discordの送信先URL（Webhook）は送信に必要なためDBへ保存されます。DBファイルは0600、新規データディレクトリは0700です。DBは暗号化されていません。バックアップにも同じアクセス制御を適用してください。HTTPログにはリクエストパス、Cookie、本文を出力しません。

Discordへ送るのは対象投稿者の公開本文と投稿リンクです。通知を受け取るXアカウントの名前、ログインCookie、PostRelayのメールアドレスや内部IDをメッセージへ含めません。通知形式の確認用に保存する生データはDiscordへ転送しません。DiscordでWebhookを作成したユーザーは、Discordの管理権限で確認できる場合があります。

Cookieを含むAngelic-Angel設定、DiscordのWebhook、DB、生の通知、実運用ログをGitへ追加しないでください。`.gitignore` は一般的な保存先を除外しますが、任意のファイル名に保存した秘密情報まで自動で検出するものではありません。

外部Python依存はありません。小さなSQLite DBと単一ワーカーで始められますが、ホスティングの採算は通知量・サポート・取得元の条件を含めて実測する必要があります。

## 管理画面

最初の「Discordへの通知」画面では、Xアカウントと届けるチャンネルの組み合わせを確認し、通知を停止・再開できます。「オン」は通知する設定であることを示し、接続の正常性や送信成功を保証する表示ではありません。

「通知するアカウントを追加」または「編集」で、Xのユーザー名・表示用のチャンネル名・Discordの送信先URLを設定します。チャンネル名を入力するだけでは実際の送信先は変わりません。送信先URLが未設定ならDiscordへ送信できません。キーワード、返信・リポスト、ロールへのメンションは「通知する内容・メンション」から設定できます。

各行の「送信履歴」で、送信対象になった通知と結果を確認できます。「送信済み」はDiscordが受け付けたことを示し、メンバーの閲覧を示すものではありません。日時はPostRelayが通知を受け取った時刻です。表示・検索は全アカウントの最新100件が対象で、アカウントごとの絞り込みもその範囲から行います。履歴のチャンネル名には現在の設定を表示し、過去に実際に送信した通知先を記録しているわけではありません。

「設定」で投稿通知の受け取り方法とDiscordへの送信先を確認できます。受け取りURLを作り直すと以前のURLは使えなくなるため、接続したツールに設定したURLも更新してください。料金・利用プラン・全アカウントの送信履歴もこの画面から開きます。
