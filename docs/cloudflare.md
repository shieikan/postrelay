# Cloudflareで使う（実験版）

PostRelayをCloudflare WorkersとDurable Objectsで動かす構成です。導入後は手元のMacやVMを常時起動する必要がありません。利用者ごとに自分のCloudflare・X・Discordの接続情報を用意します。特定のコミュニティや個人アカウントには固定されていません。

**現時点で確認したのはローカルのWorkers実行環境での動作です。** 実際のCloudflareからのX登録、長時間の受信、実際のDiscordへの配信、無料枠の使用量は未検証です。まず試験用チャンネルで確認してください。

この版は端末で設定・操作します。ブラウザーの設定画面、利用者登録、送信履歴の画面はありません。GUIを使う場合は[Docker版](server.md)を選んでください。

## 用意するもの

- CloudflareアカウントとWorkers Freeプラン。独自ドメインは不要です。
- 通知を受け取るXアカウント。通知専用のアカウントも使えます。通知対象をフォローし、対象の投稿通知をオンにしてください。
- そのXアカウントのWeb Push通知を利用できる状態と、同じログインセッションの `auth_token`・`ct0` Cookie。
- 送信先のDiscordチャンネルで作成したWebhook URL。Discord Botの常駐プロセスは不要です。
- 導入操作をするmacOS・Linux・WSLの端末、Git、Node.js 22以降とnpm。Windowsのネイティブ端末はこの設定ツールの確認対象外です。

Cookieは、Xへログインしたブラウザーの開発者ツールのCookie一覧から本人が取得します。値をチャット、Issue、スクリーンショット、コマンド引数へ貼らないでください。PostRelayはXのWeb版通知との互換性に依存します。Xの仕様変更や認証切れで停止する可能性があり、公式API契約や通知の網羅性を提供するものではありません。

## 最初の導入

### 1. ソースと依存を用意する

```sh
git clone https://github.com/shieikan/postrelay.git
cd postrelay/cloudflare
npm ci
npx wrangler login
```

ブラウザーで、自分のCloudflareアカウントへのログインを完了します。以降のコマンドも `cloudflare/` フォルダーで実行してください。

### 2. Workerを作る

`wrangler.jsonc` の `name` を、自分のアカウント内で未使用の名前に変更します。例は `community-postrelay` です。既存のWorker名を使うと、そのWorkerを更新してしまいます。その他の項目と `migrations` はそのまま使います。

```sh
npm run deploy
```

表示された `https://名前.自分のサブドメイン.workers.dev` を控えます。初回にworkers.devの有効化を求められた場合は案内に従ってください。新規作成直後は停止状態で、XやDiscordへ接続しません。`/health` はWorkerが応答するかだけを示します。

### 3. 接続情報を保存する

```sh
npm run configure
```

Worker URL、通知するXユーザー名、Discord Webhook、X Cookieを順に入力します。プッシュ通知と公開埋め込み情報だけでは投稿の種類を判定できません。種類で絞り込まずに通知する設定を確認してから進めます。監視対象による他者の投稿のリポストは、後述の `include_reposts` を有効にすると取得できます。

WebhookとCookieの入力は画面に表示しません。管理トークンと保存用暗号鍵は自動生成します。設定先は `.postrelay/settings.json` で、フォルダーは所有者のみアクセス可能、ファイルは所有者のみ読み書き可能です。既存の設定は上書きしません。

このファイルはCloudflareへの登録や復旧にも必要です。非公開の安全な場所にバックアップし、Gitへ追加しないでください。`STORAGE_KEY` を失うと保存済みの通知受信登録を復号できません。

### 4. Cloudflareへ登録して開始する

```sh
npm run secrets
npm run control -- start
npm run control -- status
```

`secrets` は設定をCloudflareのWorker Secretsへ登録します。`start` で初めてXへの通知登録と受信を開始します。設定したDiscordへの送信も有効になります。

`start` は非同期です。続けて `status` を実行し、`enabled: true`、`registered: true`、`connected: true` を確認します。これらは受信元との接続状態であり、投稿がDiscordへ届いたことの証明にはなりません。`source_paused: true` やエラーがある場合は、後述の対処を確認してください。

## 通知先や条件を変える

```sh
npm run control -- stop
```

停止後に `.postrelay/settings.json` の `config.feeds` をエディターで編集し、`npm run secrets`、`npm run control -- start` の順に実行します。[設定例](../cloudflare/config.example.json)は `config` 内部の形式です。外側の `version`、`origin`、`secrets` は残してください。

| 項目 | 設定する値 |
|---|---|
| `id` | 通知先を識別する一意の名前。英数字・`_`・`-`、1〜32文字。既存の通知先では維持する |
| `handle` | Xユーザー名。`@`なし、1〜15文字 |
| `webhook_url` | DiscordチャンネルのWebhook URL |
| `include` | いずれかを含む公開本文だけ通知する文字列の配列。空配列なら全件 |
| `exclude` | いずれかを含む公開本文を除外する文字列の配列。含める条件より優先 |
| `role_id` | 通知するDiscordロールID。メンション不要なら空文字列 |
| `enabled` | この通知先を有効にするなら `true` |
| `allow_unknown_kind` | 種類で絞り込まずに通知することを確認したら `true` |
| `include_reposts` | 監視対象によるリポストも通知するなら `true`。省略時は `false`。Xの投稿通知一覧の定期照合も有効になる |

1つの設置で最大20設定です。設定数に加え、Webhookやキーワードを含む登録用JSON全体に、UTF-8で5,000バイトの上限があります。設定ファイルのインデントはこの容量に含めません。日本語などは1文字が複数バイトになります。`secrets` は容量超過をアップロード前に検出するので、その場合は通知先やキーワードを減らしてください。この上限は[Cloudflareの1変数あたり5 KBの制限](https://developers.cloudflare.com/workers/platform/limits/#environment-variables)に収めるためのものです。

同じ投稿者を複数チャンネルへ届ける場合も、`id`を分けて追加します。文字列条件は大文字小文字を区別しない部分一致で、正規表現ではありません。設定の追加だけではX側のフォロー・投稿通知は変わりません。

送信待ちのジョブには作成時の送信先の指紋を保存します。Webhookやロールを変更すると、既存ジョブは `destination_changed` で停止し、新しい宛先には送られません。古いジョブを送る必要があれば元の送信先を復元して再送します。新しい投稿には更新後の設定を使います。

## 投稿者の表示名とアイコン

Discordの投稿カードに「表示名（@ユーザー名）」とプロフィールへのリンクを表示します。表示名は公開投稿を確認したoEmbedの情報から取得し、アイコンはXの埋め込み用データから補います。投稿IDと投稿者のユーザー名が一致した場合だけ使い、通知に含まれる私的なタイトル・本文・アイコンは転送しません。Webhook自体の名前やアイコンは変更しません。

この追加取得にX APIキーや有料APIは使いません。配信対象になった投稿について最大1回、2.5秒を上限に追加取得します。同じ投稿の複数の送信先・再送では保存済みの情報を使います。取得失敗や制限時も配信を続け、表示名がなければ@ユーザー名、アイコンがなければ画像なしで表示します。古い保存済みジョブも送信できます。

埋め込み用データは安定した公開APIではなく、仕様変更で取得できなくなることがあります。取得元の画像が古い場合や削除された場合は表示されないことがあり、最新プロフィールの保証はありません。取得したユーザーIDは投稿情報とともに保存しますが、監視対象は引き続き@ユーザー名で指定します。ユーザー名変更の自動追跡や各アカウントの全投稿の巡回は行いません。

## リポストと通知の取りこぼしの補完

`include_reposts: true` の有効な設定が1件以上ある場合、Xの投稿通知一覧を約5分ごとに取得します。プッシュ受信とは独立して動作し、同じ取得結果を全通知先で共有します。標準の間隔では1日約288回のGETです。有料X APIのキーは不要ですが、ブラウザ向けの認証済みエンドポイントを使うため、仕様変更や取得制限で動かなくなる可能性があります。

投稿通知一覧のリポスト記録から、実行アカウントのIDと元投稿のIDの関係を確認します。元投稿が公開埋め込みAPIで確認できた場合だけ送信します。カードの名前とアイコンは元投稿者のものを使い、末尾に「@監視対象 がリポスト」と表示します。通知本文や一覧の本文を公開本文の代わりに使うことはありません。

1回の取得は最新20件で、ページをさかのぼりません。初回は設置済みサービスの最終受信時刻以降を対象とし、受信履歴のない新規設置では開始時刻以降を対象とします。以後は保存済みの照合位置から補完します。監視対象の通常投稿も同時に確認し、保存済み投稿・リポストは再送しません。長期停止や短時間に多数の通知が来た場合の全件回収は保証しません。

`status` の `last_notification_sync_at` が最後の取得成功時刻、`last_notification_sync_error` が取得失敗の理由です。`next_notification_sync_at` で次の試行時刻を確認できます。取得失敗では照合位置を進めず、認証失敗・429では30分待ちます。プッシュの `connected: true` とは別に確認してください。

複数アカウントを見る場合は`config.feeds`へ追加し、通知を受け取るXアカウントで対象のフォローと投稿通知をオンにしてください。連携元アカウントの切り替えは、後述の別設置の手順に従います。

## 日常の操作

| コマンド | 動作 |
|---|---|
| `npm run control -- status` | 接続状態、件数、失敗理由、最後の受信・配信時刻を表示 |
| `npm run control -- stop` | 受信と新たな送信を停止し、再接続用のアラームを解除 |
| `npm run control -- start` | 保存済みの受信登録と送信待ちを使って再開 |
| `npm run control -- retry` | `failed` の公開確認・送信ジョブを、それぞれの処理待ちの空き容量分だけ再試行可能に戻す |

停止時点でDiscordへ送信中のリクエストは完了する場合があります。`retry` はXへの再認証を行いません。停止中に実行した場合は次の `start` まで送信しません。

`retry` は失敗時刻が古いものから再開します。一度に入りきらない失敗履歴は残すため、処理待ちが減った後で再び `retry` を実行してください。公開確認側が満杯でも、送信側に空きがあれば送信ジョブは再開できます。失敗履歴が残っていて、1件も再開できない場合は `queue_full` を返します。

ローカルの通知設定やX Cookieに誤りがあっても、`status` と `stop` は管理用情報だけで実行できます。設定ファイルのJSON形式・所有者・権限、Worker URL、管理トークンの検査は引き続き行います。設定ファイル自体を読めない場合は、非公開バックアップから復元してください。

`posts` は公開確認の件数、`jobs` は通知先ごとの送信件数です。`retry` は自動再試行待ち、`failed` は自動再試行を止めた件数です。`post_errors`・`job_errors` で理由ごとの件数を確認できます。時刻はUnixミリ秒です。`registered` は保存済みの登録の有無、`connected` は現在の接続状態です。

| 状態・エラー | 対処 |
|---|---|
| `x_auth_required` | 同じXアカウントのCookieを更新し、`secrets` → `start` を実行 |
| `push_server_backoff` | Mozillaから30分の待機指定。`next_reconnect_at` まで待つ。`start` の連打でも短縮しない |
| `public_lookup_failed`、`discord_unavailable` | 接続先の復旧を待つ。最大8回で停止したら原因解消後に `retry` |
| `discord_rate_limit` | Discordが指定した時間を待って再送する |
| `discord_rejected` | Webhookが有効か、削除・変更されていないか確認 |
| `queue_full` | 未処理が上限に到達。接続先の障害と待ち件数を確認。既存の待ちジョブは削除しない |
| `invalid_config` | 設定項目、型、一意のID、種類の扱いへの同意を確認 |
| `config_too_large` | 登録用の設定全体が5,000バイトを超えているため、通知先やキーワードを減らす |
| `invalid_admin_token` | ローカル設定の `ADMIN_TOKEN` を非公開バックアップから元の値に復元 |
| `storage_key_mismatch` | バックアップから元の `STORAGE_KEY` を復元。DBを自動初期化することはない |
| `unauthorized` | ローカルとCloudflareの `ADMIN_TOKEN` が一致するか確認 |

Cookieの更新は同じXアカウントで行います。受信するXアカウントを切り替える機能はありません。別のアカウントを使う場合は旧設置を停止し、別名のWorkerと別の設定フォルダーで新規導入します。

## 無料枠について

2026-10-07確認時点では、Workers FreeのSQLite版Durable Objectsは、実行時間13,000 GB-s/日、100,000リクエスト/日、SQL読み取り500万行/日、書き込み10万行/日、保存5 GBが無料枠です。上限を超えると該当操作が失敗し、日次枠はUTC 00:00に戻ります。[Cloudflareの料金表](https://developers.cloudflare.com/durable-objects/platform/pricing/)

この実装は、全投稿者・送信先で**1つのDurable Object**を共有します。外向きWebSocketは休眠できないため、常時稼働として計算すると `0.128 GB × 86,400秒 = 11,059.2 GB-s/日`、実行時間枠の約85%です。これは公式の計算方法に基づく概算で、実測値ではありません。[WebSocketの制約](https://developers.cloudflare.com/durable-objects/best-practices/websockets/)

同じCloudflareアカウントの他の処理、複数の設置、通知量、再接続、SQL操作にも枠を使います。無料で使い続ける場合はWorkers Freeのまま使用量を確認してください。常時稼働する設置を2つ作ると、この実行時間の概算だけで無料枠を超えます。無料運転や継続受信を保証するものではありません。

## 保存・更新時の扱い

- Cookie、Webhook、管理トークン、暗号鍵はCloudflare Secretsとローカル設定に保存します。通知受信登録の秘密鍵は `STORAGE_KEY` で暗号化してDurable Objectへ保存します。Cloudflareアカウントを信頼する構成です。
- 生通知や投稿通知一覧の本文・タイトルは保存・転送しません。候補の投稿URLとID、リポストの場合は確認済みの監視対象ユーザー名を保存します。Xの公開oEmbedで元投稿IDと投稿者を確認できた場合に限り公開本文を保存・送信します。公開確認できない内容を通知本文で補いません。
- 公開確認待ち・送信待ちはそれぞれ最大1,000件です。失敗は最大8回まで自動再試行します。履歴は稼働中に毎時整理し、終了済み送信は7日・最大2,000件、どのジョブからも参照されていない終了済み投稿も7日・最大2,000件を残します。待ちジョブとその投稿は期限で捨てません。
- 停止中は履歴整理も止まります。履歴の保存期間を超えた後の同じ投稿や、Discordが受理した直後の通信断・再起動では重複が起こり得ます。すべての投稿の取得や厳密な1回限りの送信は保証しません。
- Docker版のDB・設定との自動移行はありません。更新時は `stop`、設定の非公開バックアップ、ソース更新、`npm ci`、`npm run deploy`、`start` の順に進めます。Worker名、Durable Objectのバインド・クラス・移行定義、`STORAGE_KEY` を維持してください。

## 初回の実環境確認

1. 試験用のDiscordチャンネルを設定して開始する。
2. 通知対象の新しい公開投稿がXの通知元とDiscordに届き、本文・URL・投稿者が一致するか確認する。リポスト有効時は元投稿者とリポストしたアカウントの表示も確認する。任意の過去投稿を取得する機能はない。
3. `status` の受信・配信時刻と件数を確認し、停止・再開後も設定と送信待ちを維持できるか確認する。
4. Macを止めた状態を含めて24時間以上観測し、Cloudflareの使用量と接続・配信が継続しているか確認する。

導入した環境でこの確認が済むまでは、常用先へ切り替えたものとして扱わないでください。実装とローカル検証の範囲は[開発者向けの説明](../cloudflare/README.md)にまとめています。
